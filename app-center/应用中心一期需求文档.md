# HiTouch AI 中台应用中心一期需求文档

## 1. 文档说明

- 文档状态：产品口径已确认，已完成需求—原型一致性检查，提交研发评审
- 适用范围：应用中心一期（P0）
- 交付期望：业务期望 3～5 个工作日，最终排期由研发评估；如需拆期，必须由产品确认拆分范围，不得在研发实现中静默删除验收项
- 整理日期：2026-07-17；最后修订：2026-07-21
- 信息来源：原始业务需求、需求方逐项确认的业务边界及后续补充口径，以及对 HiTouch/Hermes 现状的核验

本文只描述“应用中心”。“Skill 中心”是另一项独立需求，不在本文范围内。

### 1.1 本次新增需求：从应用中心新建应用

本次在原有应用中心方案上新增“新建应用”能力，属于一期正式范围，并保留在交互原型中：

- 应用中心首页增加“新建应用”按钮。
- 用户输入应用需求并点击“确认”后，系统在需求前拼接 `/hitouch-superpower`，自动创建新的 Hermes Session 并发送首条消息。
- AI 在新 Session 中与用户对话并产出 HTML。
- 用户点击 Session 对话正文中的 HTML 地址后，继续使用原有的“全屏渲染器浏览/修改 → 发布到应用中心”流程。
- 点击“新建应用”本身不创建应用记录，只有最终确认发布后才创建。

本节是新增需求摘要，完整业务规则、异常处理和验收口径见 7.1、13 和 14 节；不得因本次文档整理而从原型中删除“新建应用”入口或相关交互。

## 2. 背景

产品部会通过 HiTouch/Hermes 制作解决具体业务问题的 HTML 小工具。这些工具目前主要供公司内部 PC 端使用，后续可能嵌入客户端并对外收费。

应用的维护方式可能不同：有些应用长期由一个人维护，有些应用未来可能由整个小组共同维护。考虑一期工期，先采用“单一原作者”规则保证发布、更新和使用链路闭环，共同维护能力延后建设。

目前缺少统一入口来集中展示、在线使用和持续更新这些 HTML 小工具，也缺少点赞与使用数据。同时，业务同事如果想从零制作一个新应用，仍需要先进入 Hermes 并自行组织指令，缺少面向业务用户的快捷发起入口。因此需要建设应用中心，并在其中提供 AI 辅助的新建入口。

## 3. 产品目标

1. 让同事能够从应用中心描述需求并发起新的 Hermes Session，由 AI 制作 HTML 应用。
2. 让同事把 Hermes Session 中产出的可复用 HTML 小工具发布到应用中心。
3. 让所有已登录的内部同事能够发现并在线使用应用。
4. 让原作者能够持续更新应用，同时允许其他人在原应用基础上修改并发布为自己的新应用。
5. 通过点赞人数、使用人数和使用次数，体现应用的实际价值。

## 4. 一期范围

### 4.1 一期包含

- 从 Hermes Session 对话正文点击 AI 输出的 HTML 地址，在同页全屏渲染器中预览、修改并发起发布。
- 从应用中心点击“新建应用”，输入应用需求后，由系统拼接指定 Skill 指令并自动创建新的 Hermes Session 开始制作。
- AI 辅助将相关资源整理为单个自包含 HTML。
- AI 生成应用信息并判断“更新原应用”还是“新建应用”。
- 应用列表、搜索、详情、点赞和在线使用。
- “我发布的”应用管理。
- 应用版本记录与更新说明。
- 从应用详情页或运行页点击“我要修改”，输入修改指令后携带 HTML 创建新的 Hermes Session。
- 运营后台管理全部应用。
- 在线使用和点赞的数据统计。

### 4.2 一期不包含

- Skill 中心及 Skill 管理能力。
- 除“新建应用”发起 Session 时由系统临时拼接指定 Skill 指令外，不包含应用与 Skill 的长期绑定、安装或 Skill 中心管理。
- 本地 HTML 文件直接上传。
- 应用 HTML 文件下载及下载相关统计。
- 历史 HTML 成果物批量导入。
- 多作者、小组共同维护和所有权转移。
- 面向客户或公网用户开放。
- 分类、标签、个性化推荐及更多榜单。
- 历史版本运行、切换、对比或回滚。
- 发布审批流。

## 5. 核心业务对象

### 5.1 应用

一个应用代表一个可独立运行、可重复解决明确问题的 HTML 小工具。

应用中心面向以下成果：

- 具有明确的名称、解决的问题和适用场景。
- 发布内容最终为一个自包含 HTML 文件。
- 不是一次性报告、日报、会议纪要或纯展示页面。
- 可以是完全在浏览器内运行的工具，也可以依赖外部 API。

“不是一次性内容”属于一期发布规范，不新增单独的前台人工审核步骤。AI 在生成应用信息时同时做可复用性判断；明确属于一次性报告、日报、会议纪要或纯展示页面时，作为后台阻断项在最终确认发布时说明原因并阻止提交。判断工具业务计算结果是否正确不属于该检查范围。

### 5.2 作者

- 应用首次发布时，当前登录用户自动成为原作者。
- 作者字段由系统写入，不允许发布人手动填写或更换。
- 一期每个应用只有一名原作者。

### 5.3 版本

- 首次发布自动生成版本 `1.0.0`。
- 每次更新应用 HTML，版本末位自动递增，例如 `1.0.1`、`1.0.2`。
- 版本号由系统维护，作者不能手动修改。
- 每个版本均保存版本说明；首次发布默认写入“首次发布”，更新版本由 AI 生成初稿、发布人可编辑。
- 仅修改名称、图标、解决的问题或适用场景，不产生新版本。

每个版本必须关联一份不可变的 HTML 成果快照，并记录来源 Session、来源消息、发布操作人、发布时间、版本说明和本次检测出的联网要求。应用记录保存当前版本 ID；详情页和在线使用页读取当前版本，历史版本只展示记录。应用详情中的“需要联网”随当前版本的检测结果更新。

## 6. 用户与权限

### 6.1 内部同事

所有已登录的内部同事均可：

- 查看、搜索、点赞应用。
- 在线使用应用。
- 从应用中心输入需求并创建新的 Hermes Session，由 AI 制作新的 HTML 应用。
- 通过“我要修改”输入修改指令，将应用最新版 HTML 和指令一起带入新的 Session 修改。
- 把自己 Session 中 AI 输出的 HTML 页面发布为新应用。

### 6.2 原作者

原作者除拥有普通同事权限外，还可以：

- 编辑应用基本信息。
- 更新原应用并生成新版本。
- 将修改结果另行发布为新应用。
- 下架和重新上架自己的应用。

### 6.3 管理员

不在前台设计管理员角色和权限配置。运营后台复用现有管理员登录与权限体系，管理员可管理全部应用，包括查看、编辑、更新、上架、下架和删除。

管理员更新 HTML 时同样生成新版本。

管理员管理不得改变应用原作者：

- 编辑名称、图标、解决的问题或适用场景，不产生新版本。
- 更新 HTML 时，从后台发起与前台“更新版本”一致的 Hermes 修改链路；修改成果仍需通过 HTML 渲染器确认发布，不提供本地 HTML 上传。管理员可以覆盖更新任意应用，但原作者字段保持不变，操作人另行记录。
- 上架、下架和删除均需二次确认。删除后应用对前台所有用户不可见且不可使用；一期不提供后台恢复入口，底层是否保留审计数据由研发按现有后台规范实现。

## 7. 新建与发布流程

### 7.1 从应用中心新建应用

应用中心首页提供“新建应用”按钮，所有已登录内部同事均可使用。

用户点击后：

1. 当前页面弹出应用需求输入框，不立即创建 Session。
2. 弹窗标题为“新建应用”，输入项名称为“应用需求”，用户必须填写希望应用解决的问题、使用方式或其他制作要求。
3. 用户点击“确认”后，系统创建一个新的 Hermes Session。
4. 系统在用户需求前自动拼接指定 Skill 指令，并将拼接后的完整消息作为新 Session 的首条用户消息自动发送给 AI，用户不需要再次输入或点击发送。
5. 一期暂定拼接格式为：

   ```text
   /hitouch-superpower
   {用户填写的应用需求}
   ```

6. AI 在新 Session 中与用户继续对话、澄清需求并制作新的 HTML；完成后在对话正文输出新的 HTML 页面地址。
7. 用户点击页面地址后，进入本文定义的 HTML 全屏渲染器，可继续浏览、修改或发起发布。

“新建应用”只创建制作应用的 Session，不会立即在应用中心生成应用记录。只有用户完成 HTML 制作并从渲染器确认发布后，系统才按原有发布流程创建应用。

Skill 指令暂定为 `/hitouch-superpower`，研发实现时应作为可配置项统一维护，不在前台提供 Skill 选择或编辑能力。如果 Session 创建或首条消息自动发送失败，弹窗应保留用户已经填写的需求并允许重试；同一次确认请求应做幂等处理，避免重复创建多个 Session。

### 7.2 发布入口

Hermes 完成 HTML 页面后，会在 Session 对话正文的 AI 消息中直接输出页面地址，例如 `https://site.hitouch.cc/{user}/{file}.html`。用户点击这类由平台生成、可识别为 HTML 页面的地址时：

1. HiTouch 拦截链接的浏览器默认跳转行为。
2. 不新开浏览器窗口或标签页，也不直接进入发布表单。
3. 在当前 HiTouch/Hermes 页面内打开一个近似全屏的 HTML 前端渲染器。

一期至少识别 `site.hitouch.cc` 域名下以 `.html` 结尾的页面地址；普通网页链接仍沿用原有打开规则。允许识别的域名和地址规则由研发采用白名单配置。

“发布到应用中心”只从该渲染器中发起。Workspace/Artifacts 不是本需求的 HTML 打开或发布入口，其现有文件管理行为保持不变。

一期不提供本地文件上传入口。上线前已经存在的历史 HTML 不自动进入应用中心；如需进入，由持有者在 Session 中重新发布。

### 7.3 HTML 全屏渲染器

渲染器以 HTML 实际运行内容为主要区域，并提供固定操作栏：

- 返回 Session
- 修改
- 发布到应用中心

渲染器必须保留来源 Session、来源消息、HTML 地址及本次加载的 HTML 内容快照。用户返回后仍回到原 Session，不创建新 Session。HTML 应在平台控制的前端运行容器中渲染，不通过浏览器默认行为打开新窗口。

如果 HTML 地址失效、内容加载失败或不符合允许规则，渲染器应展示失败原因和“返回 Session”，不得静默退回浏览器默认打开方式。

### 7.4 从渲染器修改

用户点击“修改”后：

1. 在渲染器内输入本次修改指令。
2. 指令不能为空。
3. 确认后返回原 Session，并把修改指令、当前 HTML 地址及内容快照自动发送给该 Session 中的 AI。
4. AI 在同一个 Session 中修改 HTML，并在新的 AI 消息中输出修改后页面地址。
5. 用户再次点击新地址进入渲染器，确认效果后可继续修改或发起发布。

渲染器内的修改指令弹窗，主按钮文案统一为“确认”。

该流程不创建新的 Session。原 HTML 地址及内容应保留，AI 输出新的修改版地址，避免直接覆盖导致无法对照。

### 7.5 自包含处理

用户点击“发布到应用中心”后，前台立即进入应用信息填写页，不展示处理中间页。若工具依赖额外的 JS、CSS、图片或数据文件，系统在后台并行尝试整理为一个自包含 HTML。

“自包含”指页面结构、样式、脚本和静态素材最终收敛在单个 HTML 中；它不等于“不能联网”。应用运行时仍可按检测结果访问外部业务 API，但不得把 API Key、Token 等敏感凭证明文写入 HTML。

- 整理过程、进度和成功结果均不向用户展示。
- 整理失败时，在用户最终确认发布时阻止提交，并说明需要处理的依赖。

### 7.6 后台检查

系统在用户填写应用信息期间，后台静默完成以下检查：

1. 确认发布对象是单个可运行 HTML。
2. 判断成果是否为可重复使用的工具，而非一次性报告、日报、会议纪要或纯展示页面。
3. 检测是否存在明文 API Key、Token 或其他敏感凭证。
4. 检测应用是否需要访问网络或外部 API。
5. 确认发布人已经通过 HTML 渲染器查看运行效果。

前台不展示“正在检查”、检查进度、检查通过清单或检查结果详情，用户对正常检查过程无感。如果发现明文敏感凭证或其他阻断问题，必须在用户最终确认发布时阻止提交，并只反馈需要用户处理的失败原因。平台不自动判断工具的业务结果是否正确。

允许发布依赖外部 API 的应用，但必须在应用信息中展示“需要联网”。外部 API 的建设、稳定性和可用性由作者或对应业务方负责，不属于应用中心职责。

### 7.7 AI 生成应用信息

用户从渲染器点击“发布到应用中心”后直接进入本信息填写页。

AI 自动生成：

- 应用名称
- 解决的问题
- 适用场景
- 应用图标
- 版本说明：首次发布默认为“首次发布”；更新时根据本次变化生成初稿

发布人可以在确认发布前编辑以上内容。作者由系统根据当前登录用户自动确定。

一期应用图标采用 emoji 或系统支持的图标标识，不支持上传图片文件；具体图标组件由研发沿用现有中台能力。

应用名称在全站范围内不能重复。比较时忽略首尾空格、连续空格差异和英文大小写；唯一范围包含已上架和已下架应用。管理员删除应用后，该名称才可以重新使用。新建或改名时如发生重名，必须修改名称后才能提交；最终以服务端唯一约束为准。

### 7.8 AI 判断更新或新建

AI 将渲染器中的当前 HTML 页面与已有应用进行比较，给出“更新已有应用”或“新建应用”的建议及理由。最终处理规则如下：

| AI 判断 | 发布人与原应用关系 | 允许操作 |
| --- | --- | --- |
| 未匹配到已有应用 | 任意用户 | 新建应用 |
| 属于已有应用的升级 | 原作者 | 自行选择“更新原应用”或“发布新应用” |
| 属于已有应用的升级 | 非原作者 | 只能发布新应用，不能覆盖原应用 |

AI 的判断用于辅助分流，不能突破作者权限规则。

相似应用检索可以使用全部未删除应用，但返回给普通用户的应用名称和详情必须遵守前台可见权限：其他作者已下架的应用不得因 AI 匹配而泄露名称或内容。遇到不可见的相似应用时，只提示“存在不可见的相似应用，本次只能按新应用提交并使用唯一名称”，不展示对方应用详情。

### 7.9 确认发布

发布人完成信息编辑、运行预览及发布方式确认后正式发布。应用发布后直接对所有已登录内部同事可见，不经过管理员审批。

最终确认发布必须由服务端重新校验后台检查结果、应用名称唯一性、更新权限和目标应用当前版本，不能只依赖前端或 AI 判断。重复点击或网络重试必须保持幂等：一次发布请求只能创建一个新应用或一个新版本。

更新原应用时以进入发布流程时的版本作为基线；若最终提交前原应用已被其他操作更新，阻止本次覆盖并提示用户基于最新版重新修改或改为发布新应用，避免旧成果覆盖新版本。

## 8. 应用发现与展示

### 8.1 应用列表

应用中心首页标题区域提供：

- “新建应用”：输入需求并发起新的 Hermes Session；
- “我发布的”：进入当前用户的应用管理页面。

应用卡片至少展示：

- 图标
- 名称
- 作者
- 解决的问题
- 适用场景
- 点赞人数
- 使用人数
- 使用次数

默认按照点赞人数从高到低排序；点赞人数相同时，当前 HTML 版本发布时间更晚的应用排在前面。只编辑名称、图标、解决的问题或适用场景，不改变该排序时间。

应用卡片不展示“需要联网”“无需外部 API”等技术属性，避免增加业务用户理解成本。确有联网要求时，只在应用详情页和实际运行页提供必要提示。

### 8.2 搜索

支持关键词搜索，搜索范围包括：

- 应用名称
- 解决的问题
- 适用场景

### 8.3 应用详情

详情页展示应用完整信息、统计数据、当前版本和版本记录，并根据当前用户身份提供“使用”“我要修改”及作者维护操作。

详情页不直接嵌入运行中的工具。用户点击“使用”后进入独立运行页。

## 9. 在线使用与继续修改

### 9.1 在线使用

- 用户点击“使用”后进入独立运行页。
- 运行页以应用 HTML 为主要工作区域。
- 在线使用始终使用应用的最新版本。
- 仅打开应用卡片或详情页不算使用。
- 应用 HTML 成功加载后，才记录一次在线使用。

### 9.2 我要修改

应用详情页和运行页提供“我要修改”入口。

点击“我要修改”后：

1. 当前页面先展示修改指令输入框，不立即创建 Session。
2. 用户必须填写本次具体修改要求。
3. 用户确认后，系统创建一个新的 Hermes Session。
4. 系统把当前应用的最新版 HTML 内容及来源信息带入新 Session，同时把用户填写的修改指令自动发送给 AI。
5. 新 Session 打开后直接进入修改处理，不要求用户再次输入或点击发送。
6. AI 完成后在对话正文输出新的 HTML 页面地址；用户点击该地址进入全屏渲染器查看、继续修改或发起发布。

详情页、在线使用页以及“我发布的”中的修改指令弹窗，主按钮文案统一为“确认”。

“我要修改”能力本身只传递 HTML 和修改指令，不绑定、安装或拼接 Skill。创建 Session 失败时应保留用户已输入的指令并允许重试；重复点击不能创建多个相同 Session。

修改完成后：

- 用户是原作者：可选择更新原应用或发布新应用。
- 用户不是原作者：只能发布新应用。

用户也可以在其他 Hermes Session 中制作出类似已有应用的新成果物；发布时仍按 AI 判断及作者规则处理。

## 10. 版本管理

### 10.1 更新原应用

更新原应用时：

- 保留原应用 ID 和访问入口。
- 保留累计点赞和使用数据。
- 新 HTML 保存为一个新版本。
- 作者填写或编辑本次更新说明；AI 可以先自动生成更新说明。
- 在线使用立即切换到最新版本。
- 若发布期间原应用版本已变化，不自动覆盖，按 7.9 的版本冲突规则处理。

### 10.2 版本记录

详情页提供“版本记录”，每个版本至少展示：

- 版本号
- 更新时间
- 更新说明
- “最新版”标识

一期历史版本仅供查看记录，不能运行、切换或回滚。

## 11. 数据指标口径

### 11.1 点赞人数

- 同一用户对同一应用最多保留一个点赞。
- 用户可以取消点赞。
- 取消后点赞人数减 1。
- 再次点赞后恢复计数，不允许通过重复点击累计多个赞。

### 11.2 使用次数

- 用户点击“使用”且应用 HTML 成功加载，使用次数加 1。
- 同一用户多次成功打开，重复累计使用次数。
- 只浏览列表、卡片或详情页不计数。

### 11.3 使用人数

- 至少成功在线使用过一次该应用的去重内部用户数。
- 同一用户多次使用，只计为 1 名使用者。

以上累计数据在应用更新版本、下架和重新上架后继续保留。

## 12. 应用状态与作者管理

### 12.1 我发布的

应用中心提供“我发布的”入口，展示当前用户：

- 已上架应用
- 已下架应用

作者可以在此进行：

- 查看详情和版本记录
- 编辑应用信息
- 更新 HTML 版本
- 下架
- 重新上架

点击“更新版本”后，用户填写修改指令并点击“确认”。确认后仍按照既定流程携带最新版 HTML 和修改指令创建新 Session，并自动开始修改。

### 12.2 下架与重新上架

- 作者下架应用后，其他同事不再能够查看或在线使用该应用。
- 已有版本、点赞和统计数据继续保留。
- 作者可以重新上架，重新上架后恢复原应用及累计数据。
- 一期作者不能自行永久删除应用；永久删除由运营后台管理员处理。

### 12.3 运营后台

运营后台沿用现有后台的页面框架和权限体系，一期至少提供：

- 查看全部已上架、已下架应用，并按应用名称、作者、状态搜索或筛选。
- 查看应用基础信息、当前版本和版本记录。
- 编辑基础信息；操作后不新增 HTML 版本。
- 发起更新版本；走 6.3 约定的 Hermes 修改、渲染器确认和发布链路。
- 上架、下架和删除；所有操作记录操作人、操作时间、应用 ID 和变更内容。

管理员操作后，前台可见性和最新版本切换规则与作者操作一致。

## 14. 一期验收标准

1. 用户点击 Session 对话正文中 AI 输出的受支持 HTML 地址时，不新开浏览器窗口或标签页，而是在当前页面打开近似全屏的 HTML 渲染器；Workspace/Artifacts 不作为该入口。
2. 渲染器提供返回原 Session、修改和发布到应用中心三个核心操作，发布只能从渲染器发起。
3. 用户从渲染器提交修改指令后，系统把当前 HTML 内容和指令自动发回原 Session，由 AI 在对话正文输出新的 HTML 地址，不创建新 Session。
4. 用户从渲染器点击“发布到应用中心”后直接进入应用信息填写页，不出现检查中间页、进度或通过清单。
5. 一期不能从本地直接上传 HTML。
6. 系统在后台静默完成自包含处理、敏感凭证和外部依赖检查；正常过程对用户无感，只有阻断问题在最终提交时反馈。
7. AI 能生成应用信息、判断更新或新建并说明理由，发布人可编辑应用信息。
8. 发布和更新前能够在渲染器中预览，发布人确认后应用直接上架。
9. 已上架和已下架应用名称按本文归一化规则全站唯一，最终提交时由服务端再次校验；管理员删除后名称可重新使用。
10. 原作者可以更新原应用或新建；非原作者不能覆盖原应用，只能新建。
11. 应用列表按点赞人数降序展示，同赞时按当前 HTML 版本发布时间降序展示，并支持指定字段的关键词搜索。
12. 所有已登录内部同事能够在线运行最新版本。
13. 在线成功加载、独立用户和点赞均按本文口径正确统计。
14. 更新 HTML 后生成连续版本号，并展示版本时间、更新说明和最新版标识。
15. 详情页和运行页的修改入口统一使用“我要修改”；用户先输入修改指令，确认后系统携带最新版 HTML 和指令创建新 Session 并自动开始修改。
16. “我要修改”创建 Session 失败时保留指令，重复提交不会创建多个相同 Session。
17. 作者能在“我发布的”中维护已上架及已下架应用。
18. 下架后其他用户不能查看或使用，重新上架后原有版本和统计仍然存在。
19. 管理员可以在运营后台管理全部应用，不需要在一期建设角色权限配置。
20. 应用中心首页展示“新建应用”按钮；点击后弹出“应用需求”输入框，空内容不能提交。
21. 用户确认新建后，系统只创建一个新的 Hermes Session，并将 `/hitouch-superpower` 与用户需求拼接为首条消息自动发送；用户不需要再次输入或发送。
22. 新建 Session 创建或首条消息发送失败时保留原需求并允许重试，重复确认不会创建多个相同 Session。
23. AI 在新 Session 中产出的 HTML 地址仍通过对话正文进入同一套全屏渲染器、修改和发布流程；点击“新建应用”本身不会直接创建应用记录。
24. 最终发布由服务端重新校验检查结果、名称唯一性、作者或管理员权限及目标版本；后台检查未通过时不能生成应用或新版本。
25. 同一发布请求重复点击或网络重试时只生成一个应用或一个版本；更新基线版本已变化时不得覆盖最新版。
26. 明确属于一次性报告、日报、会议纪要或纯展示页面的成果不能发布到应用中心；正常检查过程不在前台展示。

## 15. 延后需求

以下需求不影响一期使用，建议后续单独评估：

- 小组共同维护、增加共同作者。
- 应用所有权转移。
- 历史成果物批量导入。
- 本地 HTML 文件直接上传。
- 历史版本运行、对比和回滚。
- 分类、标签、筛选、推荐及其他榜单。
- 对外客户使用及客户端嵌入。
- 应用衍生关系展示。

## 16. 研发评审时需确定的技术方案

以下内容不再作为业务反问项，由研发在满足验收标准的前提下决定：

1. 多文件成果物整理为单一 HTML 的实现方式和失败判定。
2. HTML 安全扫描、明文凭证检测和运行隔离方案。
3. 在线 HTML“成功加载”的埋点实现。
4. Session 对话消息中 HTML 地址的识别、点击拦截、同页安全渲染、来源 Session/消息关联和返回机制。
5. 渲染器修改指令与 HTML 内容快照自动发回原 Session、原地址保留及幂等处理方式。
6. “我要修改”携带最新 HTML 和修改指令创建新 Session、自动发送及失败恢复方式。
7. AI 相似应用检索及更新/新建建议的实现方式。
8. “新建应用”创建 Session、自动发送首条消息及防重复提交的实现方式。
9. `/hitouch-superpower` Skill 指令的集中配置、可用性检查及后续替换方式。
10. 发布接口的服务端权限复核、名称唯一约束、幂等键和版本并发控制方案。
11. 运营后台操作日志及删除后的审计数据保留方案。
